# ADR-003 — لایه داده PostgreSQL

- وضعیت: **ACCEPTED**
- تاریخ: 2026-11-17
- تصمیم‌های مرتبط: D-019، D-020، D-021، D-022، D-023، D-024
- فاز: Phase 3 — Product Database, Migration & Storage Foundations

## 1. Context

محصول در فازهای ۰ تا ۲ روی دو شکل ذخیره‌سازی رشد کرده بود:

- فایل JSON برای هویت (`users.json`، `otp.json`)، دسترسی (`grants`)، و نشست‌ها.
- SQLite محلی برای `FileLibraryStore` (کتابخانهٔ فایل کاربر).

هر دو برای یک کاربر خوب کار می‌کنند و برای چند کاربر بد. مسئله فقط کارایی نیست:

- نوشتن JSON با read-modify-write انجام می‌شود؛ دو درخواست همزمان می‌توانند یکی را ببلعند.
- هیچ کلید یکتایی در سطح ذخیره‌سازی وجود ندارد، پس یکتایی شماره موبایل فقط در کد تضمین می‌شد.
- هیچ تراکنشی نیست، پس «کسر از کیف پول + ثبت مصرف» نمی‌تواند اتمی باشد.
- پشتیبان‌گیری و بازگردانی فایل‌های پراکنده روی چند مسیر، قابل اتکا نیست.

همزمان، یک schema واقعی روی Supabase پیدا شد: ۱۶ جدول و ۶ رکورد migration، از ۱۴–۱۵ نوامبر — **قبل از شروع این کار** — بدون `alembic.ini`، بدون پوشهٔ `migrations/`، و بدون هیچ ارجاعی در ریپو. آن schema فقط در دیتابیس زندگی می‌کرد.

یعنی دو منبع حقیقت ناسازگار داشتیم و هیچ‌کدام در ریپو مستند نبود.

## 2. Decision

**PostgreSQL منبع حقیقت داده تجاری است.** SQLite برای توسعهٔ محلی و آزمون باقی می‌ماند اما رفتار مرجع نیست.

اجزا:

### 2.1 بدون ORM

SQL دست‌نویس در `deeptutor/db/repositories/`.

دلیل: ریپو از قبل SQL خام دارد (`file_library.py`) و سبک موجود را نمی‌شکند. افزودن ORM یک idiomatic دوم به پروژه اضافه می‌کرد که هزینه‌اش از سودش بیشتر بود — به‌ویژه چون queries موجود به‌صورت دستی تنظیم شده‌اند (`LISTEN`، index hints، و `ON CONFLICT` صریح).

هزینه: هیچ safety net ای برای typo در نام ستون نیست. جبران: `schema_check.REQUIRED_COLUMNS` نام ستون‌ها را با نام تأیید می‌کند و migration `verify` آن را روی دیتابیس زنده اجرا می‌کند.

### 2.2 Migration مال خودمان است، نه Alembic

`deeptutor/db/migrate.py` با فایل‌های `V####__lowercase_name.sql` و نشانگرهای `-- @@ UP @@` / `-- @@ DOWN @@`.

دلیل: Alembic برای DDL تولیدشده از ORM طراحی شده. ما SQL خام می‌نویسیم، پس فقط به یک ledger نسخه‌دار و checksum نیاز داریم. علاوه بر این، checksum یک قابلیت رایگان می‌دهد که Alembic ندارد: اگر فایل migration بعد از اعمال تغییر کند، اجرای بعدی **امتناع** می‌کند. این در محیط‌هایی که DDL دستی هم اجرا می‌شود (همین پروژه، از طریق کنسول Supabase) تفاوت بین «دریفت آرام» و «شکست صریح» است.

قواعد:

- نام باید `V####__نام_کوچک.sql` باشد. یک فایل `.sql` که این الگو را نداشته باشد **خطا** است، نه نادیده‌گرفته‌شده.
- checksum = `sha256` کوتاه‌شده به ۳۲ کاراکتر.
- dialect: فایل‌های مخصوص PostgreSQL با `-- @@ DIALECT: postgres @@` شروع می‌شوند و روی SQLite تمیز رد می‌شوند.

### 2.3 ISO-8601 در مرز، `datetime` در لبه

همهٔ repository‌ها دیکشنری برمی‌گردانند با همان شکل رکورد JSON که جایگزینش می‌شوند، و timestamp‌ها **رشتهٔ ISO** هستند.

دلیل: هیچ call-site ای در فاز ۲ شکل داده‌اش تغییر نکرد. یک آزمون round-trip وجود دارد که هر ۱۱ فیلد رکورد را با نام می‌آزماید و اگر یکی گم شود fail می‌شود.

در لبهٔ PostgreSQL، `coerce_param()` رشتهٔ ISO را به `datetime` تبدیل می‌کند، چون `timestamptz` متن نمی‌پذیرد (`42804`). این تصمیم یک باگ واقعی را بست — به‌جز این، **اولین ثبت‌نام واقعی روی Supabase شکست می‌خورد**.

### 2.4 مرز سه‌لایه

```
router  →  repository  →  connection
```

- `router` دربارهٔ HTTP می‌داند، دربارهٔ SQL چیزی نمی‌داند.
- `repository` دربارهٔ شکل رکورد می‌داند، دربارهٔ HTTP چیزی نمی‌داند.
- `connection` تنها جایی است که `?` به `%s` تبدیل می‌شود.

این مرز با `import-linter` (۳ قرارداد) اعمال می‌شود، نه با حسن نیت.

### 2.5 صف، جدول است نه broker

`deeptutor/db/jobs/queue.py`.

- `enqueue` روی `dedupe_key` idempotent است (`ON CONFLICT DO NOTHING` + بازیابی شناسهٔ موجود).
- `claim` یک `UPDATE` شرطی است، پس دو worker هرگز یک job را نمی‌گیرند.
- lease پیش‌فرض ۳۰۰ ثانیه؛ worker مرده job را از دست نمی‌دهد و watchdog لازم نیست.
- حداکثر ۵ تلاش، backoff نمایی `10·2^(n-1)` با سقف ۳۶۰۰ ثانیه.

دلیل نبودِ Redis/Celery: یک dependency عملیاتی کمتر، و «بدون اثر تکراری» مستقیماً از یکتایی جدول می‌آید نه از قرارداد broker. هزینه: throughput پایین‌تر. برای بار فعلی (صفر job در Production) این معامله درست است.

### 2.6 هویت فاز ۲ مرجع است

مدل فاز ۲ برنده شد؛ schema قدیمی با `ALTER` هم‌تراز شد.

قواعد سخت:

- **هرگز `DROP`.** فقط `ADD COLUMN`، `ALTER COLUMN`، و ساخت جدول جدید.
- ایندکس‌های درست‌بودن باید **بیانیهٔ جداگانه** باشند، نه داخل `CREATE TABLE IF NOT EXISTS`.
- `REQUIRED_INDEXES` بعد از هر migration وجودشان را با نام بررسی می‌کند.

قاعدهٔ دوم از یک باگ واقعی آمد: ایندکسی که داخل `CREATE TABLE IF NOT EXISTS` تعریف شود، وقتی جدول از قبل موجود باشد **بی‌صدا رد می‌شود**. روی پروژهٔ زندهٔ Supabase، `uq_payment_provider_authority` وجود نداشت — یعنی **دو پرداخت با یک `authority` درگاه هر دو پذیرفته می‌شدند**. یک callback تکراری می‌توانست سهمیه را دو برابر کند. این باگ پول است و بی‌صدا شکست می‌خورد.

### 2.7 اتصال هویت در یک درز

`deeptutor/multi_user/identity.py` تنها یک نقطهٔ نوشتن دارد: `_write_users()`. آنجا دیتابیس وصل می‌شود.

- `_write_users()` ابتدا `users.json` را می‌نویسد، سپس `store.replace_all(users)` را صدا می‌زند. نوشتن فایل اول است تا rollback همیشه ممکن بماند.
- `replace_all` است، نه upsert. چون هر فراخوان read-modify-write زیر `_USERS_WRITE_LOCK` است و نگاشت کامل است، حذف‌ها هم منتشر می‌شوند.
- `load_users()` وقتی دیتابیس ردیف دارد، آن را ترجیح می‌دهد؛ روی دیتابیس خالی به فایل برمی‌گردد.
- `USERS_FILE.exists()` به `_store_exists()` تبدیل شد، چون «فایل نیست» دیگر معنی «کاربر نیست» را نمی‌دهد.

دلیل این طراحی: قابلیت حذف نمی‌شود (طبق قاعدهٔ کارفرما)، مسیر rollback باقی می‌ماند، و اگر دیتابیس در دسترس نباشد محصول از کار نمی‌افتد — خطا لاگ می‌شود، raise نمی‌شود.

## 3. Alternatives considered

| گزینه | چرا رد شد |
|---|---|
| SQLAlchemy 2 + Alembic | سبک دوم داده‌ای؛ DDL از ORM تولید نمی‌شود، پس autogenerate کار نمی‌کند |
| Redis + Celery برای صف | dependency عملیاتی اضافه، و «بدون اثر تکراری» به قرارداد broker وابسته می‌شد |
| SQLite برای Production | بدون یکتایی سراسری، بدون تراکنش بین پروسه‌ها، بدون کنترل دسترسی ردیف |
| سازگار کردن کد با schema قدیمی | schema قدیمی با تصمیم‌های مصوب D-005/D-006 ناسازگار است (`phone_number NOT NULL` در برابر username-is-phone) |
| گذاشتن هر دو مسیر به‌صورت موازی | دو منبع حقیقت می‌سازد؛ همان چیزی که این ADR برای حذفش نوشته شد |

## 4. Consequences

### مثبت

- یکتایی و تراکنش حالا در سطح ذخیره‌سازی تضمین می‌شود، نه در کد.
- `checksum` دریفت را صریح می‌کند.
- دادهٔ مرجع و ۱۱ کلید خارجی سالم ماندند.
- فاز ۲ بدون تغییر call-site ادامه پیدا کرد.
- مسیر rollback (فایل JSON) هنوز کار می‌کند.

### منفی / بدهی

- **مسیر شبکهٔ `psycopg` اجرا نشد.** sandbox به پورت ۵۴۳۲ نمی‌رسد، پس همهٔ DDL از طریق کنسول Supabase اجرا شد. SQL و invariant‌ها روی PostgreSQL واقعی اثبات شدند؛ اتصال درایور نه. اگر شکست بخورد، اولین `migrations up` **تراکنشی و با صفر تغییر** شکست می‌خورد.
- `backfill` از `users.json` نوشته و آزموده شد اما واقعاً اجرا نشد، چون دیتابیس زنده صفر کاربر داشت.
- `otp.py` به `OtpRepository` وصل نشد (۱۹ آزمون OTP فاز ۲ به API فایل وابسته‌اند).
- `FileLibraryStore` هنوز SQLite جدا دارد.
- Query‌های دست‌نویس safety net ندارند (جبران: `REQUIRED_COLUMNS`).

## 5. Migration & rollback

- اعمال: `python -m deeptutor.db.migrations up`
- وضعیت: `python -m deeptutor.db.migrations status`
- بررسی: `python -m deeptutor.db.migrations verify`
- SQL معکوس: `python -m deeptutor.db.migrations export --direction down`
- عقب‌گرد تا نسخه: `python -m deeptutor.db.migrations down --to V0003`

V0004 و V0005 **نباید بدون به‌روزرسانی ledger زنده ویرایش شوند**؛ checksum دریفت را رد می‌کند. این عمدی است.
