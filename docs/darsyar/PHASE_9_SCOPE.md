## ۱. شکاف‌هایی که با خواندن کد پیدا شد، نه با خواندن فهرست

ROADMAP برای فاز ۹ یازده مورد فهرست کرده است. پیش از شروع، بررسی کردم هر مورد
**الآن چه وضعی دارد**، چون فهرست می‌گوید چه باید باشد و کد می‌گوید چه هست.

| مورد ROADMAP | وضعیت واقعی در کد |
|---|---|
| `plans` table | در `V0002` ساخته شده، **صفر خط کد آن را می‌خواند** |
| `plan_code` در wallet | یک رشتهٔ آزاد؛ هیچ اعتبارسنجی‌ای ندارد |
| `plan_expires_at` | نوشته می‌شود، **هرگز بررسی نمی‌شود** |
| `require_entitlement` | پارامتر `submit` است، **هیچ فراخواننده‌ای پر نمی‌کند** |
| usage ledger مرکزی | studio جدول خودش را دارد؛ chat جای دیگری می‌شمارد |
| قیمت‌گذاری نسخه‌دار | `billing_settings` یک ردیف، بدون تاریخ اعتبار |
| custom provider | `provider_registry` دارد، ولی API/UI برای افزودن نیست |
| SSRF policy | **وجود ندارد** |
| refund/settle | در studio کامل؛ در کیف پول عمومی نه |

**نتیجهٔ مهم:** کاربری با پلن **منقضی‌شده** دقیقاً همان دسترسی کسی را دارد که
پلن فعال دارد. سه چیز جدا از هم این را می‌سازند و هر سه ناقص‌اند: جدول پلن
خوانده نمی‌شود، انقضا بررسی نمی‌شود، و hook مجوزدهی پر نشده است.

این یک **ادعای امنیتی/مالی** است، نه یک ویژگی ناقص: کسی که برای ۳۰ روز پول داده
و کسی که ۹۰ روز پیش پلن خریده و تمدید نکرده، از نظر سیستم یکی‌اند.

## ۲. دامنهٔ این پاس

### ۹.۱ — موتور entitlement (هسته)

- `PlansRepository`: خواندن، اعتبارسنجی، و **فعال‌سازی** پلن روی کیف پول.
- `entitlements.py`: یک پلن مجموعه‌ای از capabilityهاست، نه یک برچسب.
- **انقضا اجرا می‌شود**: `plan_expires_at` در گذشته ⇒ پلن منقضی، capabilityها به
  سطح پایه برمی‌گردند.
- `require_entitlement` در `submit` **سیم‌کشی می‌شود** (نه یک پارامتر مرده).
- بدون پلن ⇒ سطح پایه (free)، نه دسترسی کامل. **پیش‌فرضِ بسته، نه باز.**

### ۹.۲ — usage ledger مرکزی

- یک نمای واحد که chat tokens و media costs را با هم نشان می‌دهد.
- **idempotency**: نوشتن دوبارهٔ همان رویداد، ردیف دوم نمی‌سازد.
- **تفکیک estimated از actual** که در فاز ۸ درست شد.

### ۹.۳ — قیمت‌گذاری نسخه‌دار

- قیمت با `effective_from`؛ تغییر قیمت ردیف قبلی را بازنویسی نمی‌کند.
- هزینهٔ قدیمی با قیمت قدیمی قابل بازخوانی است.

### ۹.۴ — custom provider + سیاست SSRF

- ثبت provider سفارشی با `base_url`، و **اعتبارسنجی مقصد**.
- SSRF: localhost، IP خصوصی، metadata endpoint، و redirect.
- کلید **هرگز** به مرورگر/لاگ/شبکه برنمی‌گردد.

### خارج از این پاس، با دلیل

| مورد | چرا نه |
|---|---|
| درگاه پرداخت | ROADMAP خودش می‌گوید «تنها پس از انتخاب درگاه و ADR مستقل». درگاهی انتخاب نشده |
| deployment runbooks | بدون staging واقعی، متنِ روی کاغذ است |
| backup/restore drill | دیتابیس production وجود ندارد؛ drill روی SQLite محلی نشان می‌دهد کد کار می‌کند، نه عملیات را |
| load test ترکیبی | chat واقعی + ingest واقعی روی این host ممکن نیست |

**این‌ها را نمی‌سازم چون ساختنشان بدون شرط لازم، ادعای پوشش می‌سازد.**
