## 1. چشم‌انداز محصول

درسیار یک سامانه وب فارسی برای آموزش و یادگیری شخصی‌سازی‌شده است. این سامانه باید بتواند بر اساس پایه، شاخه، رشته، درس و منابع مجاز دانش‌آموز، نقش معلم خصوصی هوشمند را ایفا کند؛ آموزش بدهد، پرسش‌ها را پاسخ دهد، آزمون بگیرد، عملکرد را تحلیل کند و منابع آموزشی را به قالب‌های مختلف مطالعه تبدیل کند.

DeepTutor زیرساخت فنی اولیه برای اجرای Agentها، مدیریت Turn، RAG، ابزارها، قابلیت‌های آموزشی و تولید محتوای چندرسانه‌ای است. محصول نهایی باید هویت بصری، نام، مسیرهای کاربری، منطق آموزشی، مدیریت تجاری و سیاست‌های منابع مستقل درسیار داشته باشد.

### اهداف اصلی

1. آموزش منطبق با محتوای آموزشی ایران از پایه اول ابتدایی تا پایه دوازدهم.
2. نگهداری پیش‌دانشگاهی و کتاب‌های نظام‌های قدیمی در آرشیو مجزا.
3. پاسخ‌دهی مبتنی بر مجموعه منابع انتخاب‌شده و مجاز، همراه با ارجاع کوتاه و قابل فهم.
4. آزمون‌سازی، تصحیح، تحلیل نقاط ضعف و برنامه مرور.
5. مدیریت کامل کاربران، محتوا، مدل‌ها، APIها، هزینه‌ها و اشتراک‌ها از پنل مدیریت.
6. کنترل دقیق مصرف مدل‌ها و هزینه سرویس‌های چندرسانه‌ای.
7. امکان افزودن قابلیت‌ها و مدل‌های جدید بدون بازنویسی هسته.

### خارج از محدوده نسخه اولیه

- محصول Desktop مستقل؛ استقرار اصلی فقط وب است.
- دسترسی آزاد به وب برای پاسخ آموزشی به‌عنوان منبع پیش‌فرض.
- اجرای ابزارهای تحقیقاتی، شبکه‌های اجتماعی یا قابلیت‌های غیرآموزشی که در تجربه اصلی دانش‌آموز لازم نیستند.
- تضمین تراز رسمی کنکور یا نمره رسمی مدرسه؛ درسیار می‌تواند محاسبات و تحلیل‌های تعریف‌شده خودش را ارائه کند.
- تولید خودکار محتوای دارای حق نشر بدون مجوز معتبر.

## 2. کاربران، نقش‌ها و تجربه کاربری

### 2.1 نقش‌ها

حداقل نقش‌های دامنه محصول:

- super_admin: مدیر اصلی سامانه با اختیار مدیریتی سراسری.
- admin: مدیر عملیاتی با دسترسی‌هایی که super_admin تعیین می‌کند.
- teacher: نقش قابل توسعه برای مدرس یا تولیدکننده محتوا.
- student: کاربر دانش‌آموز.
- user: حساب عمومی/غیرآموزشی در صورت نیاز محصول.

مجوزها باید سمت Backend اعمال شوند. پنهان‌کردن یک دکمه در UI مجوز محسوب نمی‌شود.

### 2.2 پنل‌ها و مسیرها

- /login: ورود کاربران.
- /register: ثبت‌نام و تأیید شماره همراه.
- /: محیط اصلی یادگیری و گفت‌وگو.
- /profile: پروفایل، اطلاعات تحصیلی، تنظیمات و اشتراک.
- /admin/login: ورودی مستقل پنل مدیریت.
- /admin: داشبورد مدیریت و زیرمسیرهای مدیریتی.

پنل کاربر و مدیریت باید از نظر ناوبری، چیدمان و کنترل دسترسی مستقل باشند، ولی می‌توانند Backend و سرویس‌های دامنه مشترک داشته باشند.

### 2.3 ورود و احراز هویت کاربر

الگوی الزامی:

1. کاربر شماره موبایل را وارد می‌کند.
2. برای شماره جدید، OTP از طریق درگاه پیامک ارسال می‌شود.
3. OTP با انقضای کوتاه، محدودیت تلاش و محدودیت ارسال مجدد بررسی می‌شود.
4. پس از تأیید، حساب با شماره موبایل یکتا ایجاد و کاربر رمز عبور تعیین می‌کند.
5. دفعات بعد ورود با شماره موبایل و رمز عبور انجام می‌شود.
6. بازیابی رمز با OTP و ثبت رویداد امنیتی انجام می‌شود.

قواعد امنیتی:
- OTP خام نباید در پایگاه داده یا لاگ ذخیره شود؛ مقدار امن/هش‌شده و زمان انقضا نگهداری شود.
- شماره موبایل نرمال‌سازی و یکتا شود.
- rate limit بر اساس شماره، IP و بازه زمانی اعمال شود.
- پاسخ API نباید وجود یا عدم وجود یک شماره را برای مهاجم افشا کند.
- نشست‌ها باید قابل انقضا، لغو و مدیریت باشند.
- اتصال پیامک از طریق interface مستقل SMS Provider باشد؛ انتخاب سرویس‌دهنده و کلیدها تنظیمات محیطی/مدیریتی امن داشته باشند.
- OTP در محیط تست فقط با mock provider و کدهای آزمایشی غیرواقعی استفاده شود.

### 2.4 ورود مدیر

- مسیر ورود: /admin/login.
- نقش super_admin باید از جریان ثبت‌نام عمومی جدا باشد.
- برای توسعه محلی می‌توان bootstrap credential با username=admin و password=123 فراهم کرد، اما فقط با صراحت محیط development.
- رمز bootstrap باید در اولین ورود تعویض شود.
- Production باید در نبود secret/config امن، fail closed شود؛ هیچ رمز پیش‌فرضی اجازه ورود عمومی ندهد.
- رمز عبور به‌شکل هش مقاوم نگهداری شود؛ حتی مدیر اصلی نیز نباید رمز خام کاربران را ببیند.

### 2.5 انتخاب پروفایل آموزشی

در اولین ورود آموزشی یا پیش از اولین درس:

1. انتخاب دوره/پایه.
2. در صورت نیاز انتخاب شاخه و رشته.
3. انتخاب درس یا درس‌های مورد علاقه/مجاز.
4. امکان تأیید و اصلاح این اطلاعات از پروفایل.

طبقه‌بندی پایه جاری:
- ابتدایی: پایه 1 تا 6.
- متوسطه اول: پایه 7 تا 9.
- متوسطه دوم: پایه 10 تا 12.
- از پایه 10 به بعد شاخه و رشته در مدل داده لحاظ شود؛ همه رشته‌ها الزاماً در هر پایه فعال نیستند.
- پیش‌دانشگاهی و ساختارهای قدیمی در مجموعه آرشیوی جدا از برنامه جاری نگهداری شوند.

فهرست رشته‌ها و درس‌ها باید داده‌محور و قابل بروزرسانی از پنل مدیریت باشد؛ رشته‌ها را در کد Frontend hard-code نکن.

## 3. کتابخانه جامع منابع آموزشی

### 3.1 انواع منبع

درسیار فقط به کتاب رسمی محدود نیست. حداقل انواع زیر باید پشتیبانی شوند:

1. کتاب رسمی درسی آموزش‌وپرورش.
2. کتاب کمک‌آموزشی و شرح تکمیلی.
3. جزوه و محتوای آموزشی تأییدشده.
4. بانک نمونه سؤال، امتحان و آزمون استاندارد.
5. سؤالات کنکور و پاسخ‌نامه/تحلیل آن‌ها.
6. محتوای مکمل مجاز مانند اسلاید، متن یا منبع آموزشی دیجیتال.

### 3.2 فراداده اجباری هر منبع

- شناسه پایدار و عنوان نمایشی.
- نوع منبع و مرجع/ناشر/مولف، در صورت موجود بودن.
- پایه، دوره، شاخه، رشته و درس مرتبط.
- سال تحصیلی/سال انتشار، نسخه و زبان.
- فصل‌ها، بخش‌ها، عنوان‌ها و ساختار صفحه در صورت قابل استخراج بودن.
- کد رسمی کتاب یا شناسه ناشر، در صورت موجود بودن.
- checksum فایل و شناسه نسخه.
- وضعیت پردازش: queued، processing، needs_review، approved، rejected، failed، archived.
- وضعیت حقوقی: منبع مجاز، مدرک مجوز، محدوده استفاده، تاریخ بررسی، مالک/مسئول بررسی.
- سطح اعتبار علمی و وضعیت بازبینی.
- روابط با سؤال‌ها، پاسخ‌ها و منابع مرتبط.

فراداده داخلی کامل می‌ماند؛ همه آن لازم نیست در رابط دانش‌آموز دیده شود.

### 3.3 قواعد حقوقی محتوا

- وجود PDF در وب یا امکان دانلود به معنی مجوز پردازش، ذخیره، نمایش یا استفاده تجاری نیست.
- هر منبع قبل از عرضه باید وضعیت حقوقی و محدوده مجاز آن مشخص باشد.
- منبع فاقد شواهد کافی می‌تواند در وضعیت quarantine/needs_review بماند و نباید به‌صورت پیش‌فرض در پاسخ‌دهی تجاری استفاده شود.
- پنل مدیریت باید امکان ثبت مدرک مجوز، محدودیت استفاده و تاریخ بازبینی را داشته باشد.
- فایل‌های ورودی باید از نظر بدافزار، نوع واقعی فایل، اندازه، محتوای مخرب و محدودیت استخراج بررسی شوند.

### 3.4 سلسله‌مراتب علمی منابع

ترتیب پیشنهادی برای پاسخ‌های درسی:
1. کتاب رسمی همان پایه/رشته/درس.
2. منابع کمک‌آموزشی تأییدشده و منطبق با همان موضوع.
3. جزوه یا مرجع مکمل تأییدشده.
4. بانک سؤال و پاسخ‌نامه معتبر برای پاسخ به پرسش‌های آزمونی.

این ترتیب باید در policy و retrieval filtering اعمال شود؛ صرفاً در متن prompt نوشته نشود. تعارض منابع باید شناسایی و در صورت نیاز به کاربر توضیح داده شود.

### 3.5 ارجاع نمایشی پاسخ

ارجاع آموزشی کوتاه باشد. قالب ترجیحی:

[نام کتاب | فصل نام/شماره فصل]

برای منبعی که فصل ندارد، [عنوان منبع] کافی است. نام پایه، رشته، صفحه، chunk، شناسه فایل و سایر اطلاعات فنی در ارجاع قابل مشاهده دانش‌آموز نمایش داده نشوند. این اطلاعات می‌توانند در فراداده داخلی برای فیلتر، ممیزی و ردیابی نگهداری شوند.

### 3.6 رفتار در نبود منبع

اگر منبع مجاز و کافی پیدا نشد:
- مدل نباید پاسخ را به‌عنوان محتوای کتاب معرفی کند.
- باید صریحاً بگوید در منابع انتخاب‌شده پاسخ مستند پیدا نشده است.
- اگر سیاست مدیر اجازه بدهد، می‌توان مسیر پاسخ عمومی/وب را جداگانه و با برچسب «خارج از منابع درسی» فعال کرد؛ این مسیر نباید با پاسخ مستند کتاب مخلوط شود.
- در صورت بازیابی چند منبع ناسازگار، عدم قطعیت یا اختلاف بیان شود.

## 4. معلم هوشمند و بازیابی دانش

### 4.1 جریان پاسخ

1. احراز هویت و دریافت user profile.
2. resolve کردن پایه، شاخه، رشته و درس.
3. اعمال entitlement و مجوز منابع.
4. نرمال‌سازی سؤال و تشخیص نوع درخواست.
5. retrieval با فیلتر اجباری scope تحصیلی، وضعیت تأیید منبع و نسخه.
6. rerank و بررسی کفایت/تعارض.
7. پاسخ با زبان فارسی روان و متناسب با سن/سطح.
8. افزودن ارجاع کوتاه.
9. ثبت مصرف مدل، منابع استفاده‌شده و کیفیت/بازخورد.

### 4.2 محدودیت پایه و رشته

- فیلتر پایه و رشته باید پیش از retrieval و در سطح query/store enforce شود.
- ابزارهای RAG، خواندن منبع و capabilityها باید همان context و scope را دریافت کنند.
- کاربر نباید بتواند با prompt injection، انتخاب منبع دستی، API یا WebSocket، فیلتر را دور بزند.
- منابع archived فقط با انتخاب و مجوز روشن در مسیر آرشیو استفاده شوند.
- تغییر پروفایل باید به درخواست‌های بعدی اعمال شود؛ داده‌های گفتگوهای قدیمی با scope گذشته حفظ شوند.

### 4.3 کیفیت و ارزیابی

مجموعه آزمون ارزیابی باید حداقل شامل سؤال‌های واقعی/بازبینی‌شده در پایه‌ها و رشته‌های مختلف، پرسش مبهم، سؤال خارج از منابع، تعارض منابع، prompt injection و پاسخ‌های عددی/ریاضی باشد. معیارها: retrieval precision/recall، citation correctness، grade leakage، answer correctness، abstention correctness، latency و cost per answer.

## 5. آزمون، تمرین و بانک سؤال

### 5.1 انواع آزمون

- تشریحی: پاسخ متنی/فرمولی، مراحل حل، rubrics و نمره جزئی.
- چهارگزینه‌ای: تک‌پاسخی و در آینده چندپاسخی.
- کنکوری: زمان‌بندی، دفترچه/بخش، نمره منفی قابل تنظیم و گزارش درصد.
- آزمون هوشمند: تولید براساس فصل، مبحث، سطح دشواری و سوابق یادگیری.

### 5.2 تنظیمات آزمون

مدیر یا سازنده آزمون بتواند این موارد را تعیین کند:
- پایه، شاخه، رشته، درس، فصل و مبحث.
- تعداد سؤال، نوع و سطح دشواری.
- مدت آزمون و زمان شروع/پایان.
- منبع سؤال: بانک تأییدشده، سؤال تألیفی یا ترکیبی.
- نمره هر سؤال، نمره پاسخ غلط و پاسخ نزده.
- سیاست نمره منفی و فرمول نهایی؛ هیچ قاعده ثابت کنکور نباید hard-code شود.
- نمایش یا عدم نمایش پاسخ و توضیح پس از هر سؤال یا پس از پایان آزمون.
- ترتیب ثابت/تصادفی و shuffle گزینه‌ها.

فرمول نمره باید قابل پیکربندی باشد. پاسخ نزده به‌صورت پیش‌فرض جریمه نمی‌شود مگر سیاست آزمون صراحتاً خلاف آن را تعریف کند.

### 5.3 تصحیح

- سؤال عینی با کلید پاسخ معتبر به‌صورت قطعی تصحیح شود.
- پاسخ تشریحی با rubric، معیارها و نمره جزئی ارزیابی شود.
- نمره AI برای پاسخ تشریحی باید قابل بازبینی باشد و در موارد عدم اطمینان به‌عنوان قطعی معرفی نشود.
- نسخه سؤال، کلید پاسخ و rubric زمان آزمون snapshot شود تا تغییرات بعدی نتیجه قبلی را دستکاری نکند.
- اعتراض، بازبینی انسانی و ثبت تغییر نمره پشتیبانی شود.

### 5.4 گزارش عملکرد

گزارش شامل نمره، زمان، درصد، تعداد درست/غلط/نزده، عملکرد فصل و مبحث، روند پیشرفت و پیشنهاد مرور باشد. «تراز رسمی» تنها در صورت تعریف فرمول و داده مرجع معتبر قابل ارائه است؛ در غیر این صورت نام شاخص داخلی صریح باشد.

## 6. فلش‌کارت و مرور فاصله‌دار

- قابلیت‌های موجود Flash Cards و Mastery/Spaced Review ابتدا ممیزی و یکپارچه شوند.
- فلش‌کارت بتواند از کتاب، فصل، جزوه و اشتباهات آزمون ساخته شود.
- مرور فاصله‌دار بر اساس سابقه پاسخ و سیاست زمان‌بندی انجام شود.
- محتوای کارت به منبع تأییدشده پیوند داشته باشد.
- کارت تکراری یا بی‌منبع بدون کنترل ایجاد نشود.
- سامانه پیشرفت و موارد نیازمند مرور را ثبت کند.
- تا زمانی که ممیزی نشان نداده قابلیت فعلی ناکافی است، ماژول فلش‌کارت موازی ساخته نشود.

## 7. استودیوی محتوای آموزشی (Learning Studio)

### قابلیت‌های هدف

1. پادکست/Audio Overview با دو یا چند گوینده.
2. ویدئوی آموزشی متحرک و روایت‌شده.
3. اسلاید و ارائه آموزشی.
4. نقشه ذهنی.
5. اینفوگرافیک.
6. جزوه، خلاصه و برگه مرور.
7. در آینده محتوای تعاملی و آزمون همراه محتوا.

### اصول اجرایی

- تولید فقط با درخواست روشن کاربر یا مدیر انجام شود.
- منبع ورودی باید منابع کاربر-مجاز باشد.
- متن گفتار/اسلاید/ویدئو باید قابلیت ارجاع به منبع داشته باشد.
- خروجی در object storage نگهداری و قابل reuse شود.
- jobهای طولانی در صف پردازش انجام شوند، نه در request اصلی چت.
- وضعیت job، خطا، هزینه، مدل، زمان و فایل خروجی ثبت شود.
- قابلیت‌های موجود Audio Overview و Video Lesson ابتدا یکپارچه و فارسی‌سازی/ارزیابی شوند.
- تولید تصویر/صدا/ویدئو می‌تواند هزینه غیرتوکنی داشته باشد؛ این هزینه جدا ثبت شود.
- محدودیت‌های مجوز محتوای ورودی و خروجی رعایت شود.

## 8. مدل تجاری، اشتراک و مصرف

### 8.1 پلن‌ها

سیستم باید پلن‌های قابل تنظیم داشته باشد؛ مانند رایگان، پایه، پیشرفته و نامحدود. نام، قیمت، مدت، قابلیت‌ها، سقف مصرف، محدودیت سرعت و سیاست تمدید باید از پنل مدیریت قابل تغییر باشند. هیچ‌یک از این مقادیر نباید در کد ثابت باشند.

### 8.2 مصرف قابل ثبت

برای هر فراخوانی مدل، در صورت دسترس بودن:
- user/account, request/turn, capability.
- provider, model, route/profile.
- input, output, total, cached, reasoning tokens.
- actual vs estimated usage و دلیل estimate.
- مدت اجرا، وضعیت موفق/ناموفق و شناسه idempotency.
- هزینه محاسبه‌شده با نسخه تعرفه استفاده‌شده.

برای سرویس‌های غیرتوکنی:
- ثانیه/دقیقه صوت و ویدئو.
- تعداد تصویر/عملیات.
- پردازش OCR یا unitهای اختصاصی Provider.
- هزینه سرویس خارجی و نرخ تبدیل/قیمت‌گذاری.

### 8.3 حسابداری اعتبار

- قبل از اجرای عملیات قابل صورتحساب، اعتبار/سهمیه رزرو شود.
- پس از دریافت usage واقعی، رزرو تسویه شود.
- در شکست/لغو، بخش استفاده‌نشده آزاد شود.
- عملیات reserve/settle/refund باید اتمیک و idempotent باشد.
- مدل قیمت‌گذاری و نرخ تبدیل باید نسخه‌بندی شود.
- اگر provider آمار واقعی ارائه نداد، مقدار تخمینی با برچسب estimated نمایش داده شود.
- هزینه واقعی Provider از مبلغی که به کاربر کسر می‌شود جدا نگهداری شود.
- تاریخچه تراکنش‌ها قابل حذف یا بازنویسی خاموش نباشد؛ اصلاح با تراکنش جبرانی انجام شود.

### 8.4 کنترل هزینه

- انتخاب مدل اقتصادی برای کارهای سبک.
- مدل قوی‌تر فقط برای کارهایی که نیاز دارند.
- محدودیت context و retrieval chunks.
- caching پاسخ/embedding/خروجی‌های قابل استفاده مجدد با رعایت scope.
- سقف jobهای چندرسانه‌ای و تعداد تلاش مجدد.
- بودجه per-user، per-plan و per-capability.
- هشدار مصرف و قطع ایمن در عبور از سقف.

## 9. مدیریت کامل سامانه

### بخش‌های پنل مدیریت

- داشبورد و آمار کسب‌وکار.
- کاربران، نقش‌ها، وضعیت حساب، پایه/رشته و بازیابی رمز.
- مدیریت والد/سرپرست در صورت فعال شدن سیاست محصول.
- دوره‌ها، پایه‌ها، شاخه‌ها، رشته‌ها و درس‌ها.
- کتاب‌ها، منابع، نسخه‌ها، مجوزها و وضعیت پردازش.
- بانک سؤال، آزمون‌ها، rubricها و نتایج.
- مدل‌ها، Providerها، API endpointها و routing policy.
- پلن‌ها، قیمت‌ها، اعتبار، تراکنش‌ها و گزارش مصرف.
- قابلیت‌های Learning Studio و محدودیت‌های آن.
- promptها، policyها و تنظیمات بازیابی.
- گزارش رویدادها، رخدادهای امنیتی و عملیات مدیران.
- تنظیمات عمومی، SMS provider، ذخیره‌سازی، workerها و سلامت سرویس.

### حدود اختیار و امنیت

Super Admin اختیار تغییر تنظیمات تجاری و عملیاتی سامانه را دارد؛ با این استثناهای امنیتی:
- رمز عبور خام هیچ کاربری قابل مشاهده نیست؛ فقط reset/set با workflow امن مجاز است.
- API key خام فقط در فرم امن ورود/تعویض مدیریت می‌شود و پس از ذخیره قابل بازیابی از UI نیست.
- پنل مدیریت مجوز اجرای shell/کد دلخواه روی سرور یا خواندن فایل‌های محرمانه runtime را نمی‌گیرد.
- عملیات حساس باید audit log شامل actor، action، target، timestamp، request id و نتیجه داشته باشند؛ از ثبت secret و داده حساس در log جلوگیری شود.
- حذف کاربران و داده‌ها باید سیاست retention و قابلیت soft-delete/restore متناسب با نیاز قانونی داشته باشد.
- مدیریت نقش و دسترسی به‌صورت least privilege برای مدیران غیر اصلی اعمال شود.
- MFA برای مدیران در مسیر Production توصیه/الزام شود.

## 10. Custom AI API و مسیریابی مدل

پنل مدیریت باید افزودن/تغییر/حذف/آزمایش endpointهای اختصاصی را پشتیبانی کند.

حداقل امکانات:
- Provider name، Base URL، API protocol، model id/name، API key و extra headers.
- پشتیبانی از OpenAI-compatible و adapterهای native موجود.
- تست اتصال و تست فهرست مدل‌ها در صورت پشتیبانی.
- redaction کامل کلیدها و headerهای محرمانه در API/UI/log.
- انتخاب مدل مستقل برای chat، task/light, embeddings, reranking, OCR/vision, TTS, STT, image generation و video generation.
- fallback و timeout/retry قابل تنظیم.
- محدودیت concurrency، token/context و budget.
- کنترل مدل‌های مجاز برای هر پلن یا قابلیت.
- ثبت provider/model واقعی مصرف‌شده در usage ledger.

هر endpoint سفارشی یک ورودی غیرقابل اعتماد است: SSRF protections، allow/deny rules، HTTPS policy و جلوگیری از دسترسی به شبکه/metadata داخلی باید بررسی و پیاده‌سازی شوند. آدرس Provider و secret هرگز به مرورگر کاربر نرود.

## 11. هویت محصول و رابط

- نام نمایشی محصول: درسیار.
- برند فنی در رابط عمومی نباید DeepTutor را به‌عنوان محصول اصلی نشان دهد.
- namespaceها و packageهای داخلی deeptutor در مرحله اول بدون دلیل مهاجرتی rename نشوند.
- زبان پیش‌فرض فارسی، direction برابر RTL، تقویم و اعداد فارسی در سطح UI با سیاست یکپارچه.
- طراحی responsive برای موبایل/تبلت/دسکتاپ.
- صفحه ورود و پنل مدیریت از نظر بصری اختصاصی و با هویت درسیار.
- accessibility، حالت loading/error/empty و پیام‌های قابل فهم.
- نمایش ارجاع منبع کوتاه در پیام‌ها و خروجی‌های آموزشی.

## 12. کیفیت، امنیت و قابلیت اعتماد

- Backend authorization برای تمام API/HTTP/WebSocket routes.
- tenant/user scope isolation برای فایل‌ها، گفتگو، منابع، آزمون و خروجی‌ها.
- CSRF/CORS/cookie/session policy بررسی شود.
- rate limiting، account lockout policy و OTP abuse controls.
- رمزنگاری ارتباطات و محافظت از secrets در rest/in transit.
- file validation، zip/decompression limits، parser sandbox و محدودیت منابع.
- prompt injection و document instruction isolation؛ متن داخل PDF دستور اجرایی برای agent نیست.
- backup، restore drill و migration rollback.
- observability با حذف PII و secrets.
- تست‌های unit، integration، API contract، browser E2E، load، security و RAG evaluation.
- خطاهای Provider نباید موجب کسر اعتبار غیرمجاز شوند.
- هر قابلیت جدید باید رفتار در timeout، cancellation، retry و duplicate request را مشخص کند.

## 13. معیارهای پذیرش سطح محصول

نسخه قابل عرضه تجاری زمانی آماده است که:
1. کاربر با شماره موبایل تأییدشده ثبت‌نام کند و با شماره/رمز وارد شود.
2. مسیر مدیریت مستقل و role enforcement واقعی داشته باشد.
3. مدیر بتواند کاربران و منابع را بدون دسترسی به رمز خام مدیریت کند.
4. پروفایل تحصیلی در همه مسیرهای پاسخ و آزمون اعمال شود.
5. پاسخ‌دهی grade/track leakage نداشته باشد در مجموعه آزمون تعریف‌شده.
6. پاسخ‌های آموزشی ارجاع کوتاه و قابل تأیید داشته باشند.
7. نبود شواهد کافی به abstention منجر شود، نه hallucinated citation.
8. منابع حقوقاً نامشخص تا تأیید، خارج از retrieval تجاری باشند.
9. آزمون تشریحی/تستی و نمره منفی با پیکربندی قابل تست باشند.
10. مصرف واقعی/تخمینی و هزینه غیرتوکنی ثبت و گزارش شوند.
11. reserve/settle/refund در خطا و درخواست تکراری درست باشد.
12. Custom API بدون افشای secret قابل تنظیم و آزمایش باشد.
13. تولید صوت/ویدئو job-based، قابل لغو و قابل صورتحساب باشد.
14. عملیات حساس ادمین audit log داشته باشند.
15. تست‌های لازم، backup/restore و امنیت قبل از Production پاس شوند.

## 14. اصل توسعه

درسیار باید با حفظ هسته مفید DeepTutor به شکل افزایشی ساخته شود. حذف ماژول فقط پس از dependency audit، مالکیت source، test inventory، بررسی وابستگی manifestها و اثبات نبود مصرف‌کننده مجاز است. هر تغییر داده‌ای migration و rollback دارد. هیچ Phase با صرف وجود UI یا کد اسکلت‌شده COMPLETE اعلام نمی‌شود.
